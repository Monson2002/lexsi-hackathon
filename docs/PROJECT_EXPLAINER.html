1. The goal in plain words

We build a small language model that reads a document and fills in a form. The form is a JSON Schema. The answer is one JSON object.

Here is an example. The document is a receipt. The schema asks for the shop name, the date, and the total. The model must return the three values in the correct format. If the receipt has no value for a field, the model must write null.

Document+JSON Schema→Model→One JSON object

The model must learn the general skill of "follow any schema". It must not learn one fixed form. We prove this with schemas and a domain that the model never saw in training.

The rules of the hackathon

  • This is the Lexsi Labs hackathon, Track 1: fine-tuning and data curation.
  • The model that we fine-tune must be a Cohere Labs open-weights model. We use Tiny Aya Global (3.35 billion parameters).
  • Other models are allowed only in a supporting role. Examples are a teacher, a judge, or a price comparison.
  • We must chain at least two of three toolkits: CuratorKIT, AlignTune, and AuditKIT. We use all three.
  • All data must be synthetic or public. We must not use real personal data.
  • Everything must be public on Hugging Face and on GitHub.

2. Theory you need first

2.1 Language model and token

A language model is a program that predicts the next piece of text. The pieces are called tokens. A token is a word or a part of a word. The model reads the tokens of the prompt. Then it writes one new token at a time until it decides to stop.

Our prompt is long. The schema and the document together are about 1,200 tokens or more. The answer can have up to 1,280 tokens.

2.2 Parameters and fine-tuning

Parameters are the numbers inside the model. They store what the model knows. Tiny Aya Global has 3.35 billion of them. Fine-tuning means that we change these numbers a little with new examples. The model then does a new task better.

2.3 LoRA, quantization, and QLoRA

To change all 3.35 billion numbers needs a large GPU. We do not have one. LoRA is a trick that solves this. We freeze the original numbers. We add small extra matrices (an "adapter") and train only these.

Our adapter has 60,456,960 trainable parameters. This is about 1.8 percent of the model. The adapter file is about 242 MB.

Quantization stores the frozen numbers with fewer bits. We use 4 bits (the NF4 format). This makes the model small enough for a free Kaggle T4 GPU. LoRA on a 4-bit model is called QLoRA.

2.4 JSON and JSON Schema

JSON is a text format for data. It has objects (key and value pairs), arrays (lists), strings, numbers, true, false, and null. A JSON Schema is a JSON document that describes what a valid JSON object looks like. It states the keys, the types, the allowed values (enums), and which keys are required.

{ "type": "object",
  "properties": { "date":  {"type": ["string","null"], "format": "date"},
                  "total": {"type": ["number","null"]} },
  "required": ["date", "total"] }

In our training data, every key is required and every value can be null. A missing value is an explicit null. This makes "missing field" a clear skill that we can measure.

2.5 The output rules the model must follow

  • The output is valid JSON and it follows the schema.
  • Each value comes from the document. The model must never invent a value.
  • If the document does not contain a value, the model writes null.
  • The model changes a value only when the schema asks for it. Example: a date in YYYY-MM-DD format.

2.6 The frozen prompt format

Training and evaluation must use exactly the same prompt. If the format changes, all data and all results become invalid. The format is frozen. It has a system message and a user message.

SYSTEM: You extract structured data. Return only a single JSON object that
conforms to the given JSON Schema. Use null for values that are not present
in the document. Do not invent values. Do not add explanations or markdown fences.

USER:   <JSON_SCHEMA> ...schema... </JSON_SCHEMA>

        <DOCUMENT> ...document text... </DOCUMENT>

2.7 SFT: supervised fine-tuning

In SFT we show the model many pairs of (prompt, correct answer). The model learns to copy the correct answer. We compute the loss only on the answer tokens. The prompt tokens do not count. In our data, the answer is about 14 percent of the tokens.

SFT is simple and it works well. Its limit is that the model sees only correct answers. It never learns what a wrong answer looks like.

2.8 DPO: direct preference optimization

In DPO we show the model pairs of answers for the same prompt. One answer is "chosen" (good). One answer is "rejected" (bad). The model learns to make the good answer more likely and the bad answer less likely.

DPO uses a reference model. The reference is the model before DPO. In our case the reference is SFT v2. The parameter beta controls how far the new model can move from the reference.

A check that proves the setup is correct. At step 0 the new model and the reference are the same. The DPO loss must then be ln 2, which is 0.693. If the first loss is different, the run is wrong and we must not use it.

2.9 Reinforcement learning (RL) and GRPO

In RL the model writes an answer. A reward function gives a score. The model learns to get higher scores. GRPO is one RL method. We tried a GRPO adapter early in the project.

RL has a known danger: reward hacking. The model finds a trick to get a high score without doing the task.

For our task, the trick is to return all null. This output is always valid against the schema. It is sometimes correct. A bad reward makes the model use this trick. This is why RL is optional for us.

2.10 On-policy and rule-based data

"On-policy" data comes from the model itself. We let the SFT v2 model answer new prompts. Its wrong answers become the rejected side of a pair. These pairs show the real mistakes of the model.

"Rule-based" data is made by code. We take the correct answer and corrupt it on purpose. Examples are a deleted value, a wrong type, or a wrong date format. This is cheap. Its risk is that the model can never make these mistakes. We use both kinds.

2.11 Data splits and leakage

SplitWhat it containsWhat it tests
trainTraining schemas and documentsNot used for scores
valNew documents, schemas that the model sawDoes the model work on new documents?
test (also called test_a)New schemas, domains that the model sawDoes the model work on new schemas?
test_bA whole new domain (FieldBench)Does the model generalize to a new domain?
test_cReal public documents (receipts)Does the model work on real, messy text?

Leakage means that a schema or a near copy of it appears in two splits. Leakage makes the scores look better than the truth. We split at the schema level before we generate or remove duplicates. We run a leakage check after each data change.

2.12 Metrics

MetricMeaning
parse_okThe output is valid JSON.
schema_validThe output is valid JSON and it follows the schema.
field_f1A score for each field value, compared with the correct answer. Correct nulls count.
doc_exactAll fields in the document are correct.
null_accThe model handles missing fields correctly.
hallucination_rateThe share of values that the document does not support.

Why schema validity is not our main result. A technique called constrained decoding forces any model to write valid JSON. Validity is then near 100 percent for every model. It does not show that the values are correct. Our main results are field_f1 and doc_exact, and the gap between val and the test sets.

2.13 Greedy decoding and sampling

Greedy decoding means that the model always picks the most likely next token. It gives one answer for each prompt. We use it for evaluation, so results are repeatable. Sampling picks tokens at random from the likely ones. We use sampling at temperature 0.7 to collect the varied mistakes of the model for DPO.

2.14 Paired bootstrap and McNemar test

A small difference between two models can be luck. We test this. The paired bootstrap resamples the test documents many times and gives a confidence interval for the difference. If the interval is fully above 0, the improvement is real. The McNemar test does a similar check for documents where one model is right and the other is wrong.

4. What we tried, in order

4.1 First baseline: base model, SFT, and GRPO

Sujal built the first dataset and notebook. We built an evaluation harness and compared the base model, an early SFT adapter, and a GRPO adapter. We evaluated on the val and test splits.

The first results had problems that we had to find and fix:

  • Identical numbers for different models. AuditKIT keeps a cache of runs. The key was the model name. Different adapters with the same name gave the cached result. Now the model name always includes the token limit and the precision.
  • An adapter with no training. We found that one early adapter had all-zero LoRA B matrices. This means that it did not change the model at all. We now check that the LoRA weights are not zero.
  • Answers that were cut off. A limit of 384 new tokens cut long answers. We tested 1,280, 1,536, and 2,048 tokens. Base and GRPO gave identical outputs for these three. We use 1,280.
  • Silent wrong flags. The script ignored unknown command-line flags. It now stops with an error.

4.2 Harder test sets: FieldBench

The first test sets used the same six document templates as training. They flatter the model. We added FieldBench as test_b (a new domain, 415 documents) and test_c (real receipts, 143 documents). These sets show the real generalization.

The first big finding. The early SFT adapter scored 0.983 document-exact on val. On test_b it scored 0.010. It memorized the templates. This is the problem that the rest of the project tries to fix.

4.3 Diagnosis: why did the model fail?

We made an error taxonomy. It counts the type of each failure. The main finding for the base model on test_b was this: 82 of 100 documents had a date that the model did not normalize to YYYY-MM-DD. The early SFT data had dates in the same format as the answer. The model never learned to convert dates.

The other weaknesses were fenced answers (markdown code blocks around the JSON), numbers with separators, and enum labels that the document wrote in another way.

4.4 Better data for SFT v2

We rebuilt the training data. The plan was diversity, not volume. Three sources went into one pool:

SourceRowsNotes
Sujal's dataset, augmented by our code1,433Dates written in other ways. Amounts with separators. Enum labels reworded. One to three fields removed from the text, with answer null.
Schema-first rows from the structure of real schemas (JSONSchemaBench)1,176Field names, nesting, enums, and $defs come from real schemas. Our code generates the values and the documents. No LLM is used.
Converted rows from paraloq/json_data_extraction151The licence is not clear (see section 7).

The gold answer is exact by construction. We sample a record from the schema first, and then write the document from it. We do not use "an LLM extracts the answer" as gold.

The CuratorKIT pass: 2,994 rows went in, 140 near-duplicates and 22 secrets false-positives were removed, and 2,832 remained. A length limit and a split guard then left 2,760 rows. One row was too long for training, so training used 2,759.

4.5 A data mistake that we found and fixed

Sujal pushed a new version of the dataset. It moved old training rows into val and test. Our first SFT v2 build then had leakage. 88 of 120 val rows and 84 of 120 test rows shared field-name sets with training. A results-verification script found this because ids were missing.

We rebuilt the data from the current dataset. We pinned the dataset revision (e26e691b). We added a split guard that removes any training row whose schema or field-name set appears in an evaluation set.

The final SFT v2 run took 346 optimizer steps in 4 hours and 39 minutes on one Kaggle T4. The last training loss was about 0.003.

5. The current approach

The plan has two stages. Stage 1 is SFT v2, and it is done. Stage 2 is DPO on top of SFT v2, and it is in progress. SFT alone is a valid submission. DPO must not block the deadline.

Curated data→SFT v2 (AlignTune)→Sample mistakes→Build pairs→DPO (AlignTune)→Evaluate (AuditKIT)

5.1 Why DPO after SFT?

The evaluation of SFT v2 showed new weaknesses.

The model writes null when the document has a value. It makes bracket errors in nested JSON. It writes a list in a string slot. It adds keys that the schema does not have. DPO shows the model these mistakes as "rejected" answers.

5.2 The success rule, fixed before the run

We wrote the rule before we saw any DPO result. This prevents us from choosing a rule that fits the result.

  • On test_b: the paired difference in doc_exact and in field_f1 must have an interval above 0.
  • On test_c: the interval of field_f1 must be above 0, and doc_exact must not be lower.
  • On val and test: no significant drop. parse_ok and schema_valid must not fall more than 1 point.

If the rule fails, we report that DPO did not help. We do not change the rule.

5.3 The phases

  1. Phase 1: sample the mistakes of SFT v2. The model answers 2,081 new prompts.
    • The prompts use new schemas from JSONSchemaBench (val and test parts). The documents come from our schema-first generator.
    • No prompt overlaps training data or any evaluation set.
    • The model uses sampling at temperature 0.7. The script never reads the gold answers.
    • The script writes a metadata file with the adapter commit and the weights hash.
    • The run is resumable, and the prompts are in random order. A run that stops early is still a fair sample.
  2. Build the pairs. We compare each sample with the gold.
    • A wrong answer becomes "rejected". The gold becomes "chosen".
    • We add 1,162 rule-based pairs.
    • We change the mix to give more weight to over-null, wrong type, broken JSON, and extra keys.
    • CuratorKIT removes duplicates.
  3. Merge SFT v2 into the base weights. AlignTune uses "adapter off" as the DPO reference. With SFT v2 inside the weights, the reference is SFT v2.
  4. Smoke test. A short run on a few pairs. The first-step loss must be about 0.693.
  5. Train DPO. One epoch. A new LoRA (rank 16) on top of the merged model. The learning rate of 1e-5 is an untuned starting point. We do not tune it on val, test, or FieldBench.
  6. Evaluate five systems on the same four splits: base, old SFT, SFT v2, a merged SFT v2 control, and SFT v2 plus DPO. The merged control shows what the merge itself changes, so we do not mistake it for a DPO effect.
  7. Verify and compare. A script recomputes all metrics from the raw outputs. Another script applies the success rule.

5.4 Details that made the DPO setup correct

  • AlignTune turns message lists into plain strings. The system prompt then joins the user text, and the chat template is never used. We render the chat template ourselves into strings. We removed the first BOS token because TRL adds one. We checked that the token ids equal the chat-template ids for 600 of 600 sequences.
  • TRL has a default maximum length of 1,024 tokens. Our prompts alone have about 1,200. The answers will be cut off. We set the length to 2,048 and drop pairs that do not fit.
  • TRL turns on bf16 by default. We set the precision by hand.
  • The reference check: on a tiny test model, the first-step loss was 0.6931 and the reward margin was 0.

5.5 The time limit

Gate 3: the DPO adapter must exist by the evening of Nov 13. If it does not exist, we drop DPO. We then submit SFT v2 with a full evaluation. This is a valid result.

6. Results so far

These numbers come from the evaluation that James ran with his own SFT v2 adapter. The adapter on Hugging Face (monson2002/tiny-aya-sft-v2-adapter) was trained on Kaggle. It has not been evaluated yet. DPO has no results yet. We do not report a number that we cannot trace to a run.

SFT v2 keeps the high in-domain score. It also removes the collapse on the new domain. On test_b it is 3.6 points above the base model. This difference is not statistically significant (interval -0.7 to +8.0, McNemar p = 0.12).

6.2 Other findings

  • test_b field_f1: base 0.794, SFT v2 0.783. This difference is not significant.
  • test_c field_f1: base 0.448, SFT v2 0.484. This improvement is significant (interval +1.0 to +6.2). doc_exact is 0 for all systems on test_c.
  • On test_b, parse_ok fell from 1.000 (base) to 0.957 (SFT v2). This is a significant drop. The cause is broken nested JSON.
  • Unnormalized dates: 82 of 100 documents for the base model on test_b. SFT v2 has none.
  • Fenced answers: gone.
  • New weakness, over-null: 64 per 100 documents on test_b. The base model has 1.4. The nulls concentrate on currency, subtotal, and form type, where the gold value is inferred or normalized.

The honest summary. SFT v2 fixes the main in-domain failures and does not collapse on a new domain. It does not yet prove a clear gain over the base model on the new domain. DPO is our attempt to fix the remaining weaknesses.

7. Limits and open questions

  • Synthetic data. The training documents are template-like. Real documents with OCR noise, long text, and tables are much harder. test_c shows this: no document is fully correct.
  • In-domain scores are optimistic. About 78 to 81 percent of the answer strings in val and test also appear in the training answers. Judge generalization on FieldBench.
  • Two SFT v2 adapters exist. James's adapter (bf16) was evaluated. The Hugging Face adapter (fp32, from Kaggle) was used as the DPO base. We must evaluate it to know if it matches.
  • Licence of the paraloq rows. The Hub tag says Apache-2.0. The dataset card says "intended for research purposes only". The licence is not resolved. The team must decide: keep the note, confirm the terms, or retrain without these 151 rows.
  • Licence of the model. The base model uses CC-BY-NC-4.0 (non-commercial). Our adapter uses the same licence.
  • Speed. The SFT v2 evaluation took 12.9 seconds for each document on James's machine. The early SFT took 2.2. We do not know the cause. GPU contention is the likely reason.
  • Still to do for the submission: a README with reproduction steps, a write-up, and an abstract under 500 words. We also need a demo Space and a cost comparison with a closed model. The datasets and logs must be public on Hugging Face.

8. Glossary

TermMeaning
AdapterA small set of extra trained numbers (LoRA) that you add to a frozen model.
Base modelThe model before any fine-tuning. Here: Tiny Aya Global.
Chosen / rejectedThe good answer and the bad answer in a DPO pair.
Constrained decodingA method that forces the output to follow a grammar or a schema.
DPODirect preference optimization. Training on pairs of good and bad answers.
GoldThe correct answer for a document. We make it before we write the document.
HallucinationA value in the output that the document does not support.
LeakageThe same schema or a near copy appears in two splits.
LoRA / QLoRATraining of small extra matrices. QLoRA does this on a 4-bit model.
NullThe JSON value for "not present in the document".
Over-nullThe model writes null where the document has a value.
Reference modelThe model that DPO compares against. Here: SFT v2.
Reward hackingThe model gets a high score with a trick, and not by doing the task.
SFTSupervised fine-tuning. Training on pairs of prompt and correct answer.
TokenA word or a part of a word. The unit that a model reads and writes.
